# cold-path-warmup

Я меряю, насколько первый вызов торгового обработчика после паузы медленнее горячего и какой прогрев эту разницу сокращает. Конфигурация такая же, как в latency-critical системах. Критичный поток живёт на выделенном ядре и выполняет busy-poll цикл. Глубокий сон на этом ядре запрещён.

| Документ | О чём |
| --- | --- |
| [docs/shadow.md](docs/shadow.md) | shadow execution, то есть прогон обработчика в режиме dry run. В цикле, через сон и на реальном потоке, с ценой и хвостами |
| [docs/prefetch.md](docs/prefetch.md) | программный prefetch кода и данных. Что он возвращает и когда он выгоднее shadow execution |

## Метрики и термины

- **Горячий вызов** — 64-й вызов обработчика подряд, без пауз. На моём обработчике он занимает 117 нс.
- **Холодный (первый) вызов** — первый вызов после паузы длиной Δt. Пауза проходит одним из способов ожидания. Это может быть сон, busy-poll цикл, цикл с прогревом и так далее.
- **Штраф** — главная метрика. Это p50 первого вызова минус p50 горячего вызова в том же запуске, в наносекундах. По штрафу видно, сколько стоит остывание. Сравнение идёт внутри одного запуска, и так уходит разница между процессами.
- **«Событие → конец»** — задержка от момента события до конца первого вызова. Если поток спал, сюда входит и опоздание пробуждения. На онлайн-стенде это время от метки ядра ОС на пакете до конца обработчика.
- **Сокращение штрафа** — на сколько процентов прогрев уменьшил штраф по сравнению с тем же способом ожидания без прогрева. Я считаю его, только если штраф без прогрева надёжно больше 50 нс. Иначе процент сильно меняется от шума.
- **Цена прогрева** — сколько времени ядра уходит на прогрев. Это длительность прогонов, делённая на период T, в процентах ядра.
- **Хвосты** — p99 и p999. Квантиль я принимаю, только если за ним не меньше 10 точек. Поэтому в `bench` p999 считается только в сериях по 20 тысяч испытаний. Основной источник хвостов — онлайн-стенд с миллионами пакетов.
- **Повтор** — новый запуск процесса с другим seed и другим размером окружения, чтобы раскладка памяти не давала преимущества одному варианту ([Mytkowicz et al.](https://users.cs.northwestern.edu/~robby/courses/322-2013-spring/mytkowicz-wrong-data.pdf)). Шум между ядрами и запусками я оцениваю A/A-сравнением. Это когда один и тот же способ запускается на двух ядрах.
- **Shadow execution** — прогон обработчика по тому же пути, что у настоящего события, но в режиме dry run. Стратегия при этом не отправляет заявку, и стакан после прогона остаётся тем же.
- **Prewake** — проснуться за δ до известного момента события, сделать прогон в режиме dry run и дождаться события в цикле.
- **Prefetch** — инструкции `prefetcht0` и `prefetcht1` по адресам кода и данных обработчика. Сам код при этом не исполняется.
- **Δt, T, δ** — длина паузы, период прогрева и запас до события. δ показывает, за сколько до события поток просыпается в режимах prewake и pfwake (в замерах 200 мкс). Запас должен быть больше опоздания пробуждения, иначе событие придёт раньше, чем закончится прогрев.

**Время.** Каждый вызов замеряется в окне `lfence; rdtsc … rdtscp; lfence` по [рекомендации Intel](https://www.intel.com/content/dam/www/public/us/en/documents/white-papers/ia-32-ia-64-benchmark-code-execution-paper.pdf). Частота ядра закреплена, поэтому такт TSC переводится в наносекунды напрямую.

**Счётчики процессора.** Я открываю их группой из 3–6 событий через `perf_event_open` ([counters.cpp](src/bench/counters.cpp)) и читаю инструкцией `rdpmc` прямо из пользовательского пространства, до и после замеренного вызова, без системного вызова. По умолчанию счётчики не считают ядро ОС. Время я беру только из запусков без счётчиков. Сначала я читал счётчики через `read()`. Этот системный вызов стоял у самого окна. Он делал горячий вызов на 15% дольше и сам грел цикл. С `rdpmc` добавка 3–5 нс ([Weaver, 2017](https://web.eece.maine.edu/~vweaver/projects/papi-rdpmc/2017_espt_draft.pdf)). Группа выбирается флагом `--group`.

| Группа | События |
| --- | --- |
| a | промахи L1d, промахи LLC, branch misses |
| b | такты, опорные такты (частота), промахи L1, L2 и L3 по загрузкам, промахи L1i |
| c | код мимо L2, простои выборки, BTB re-steers (`baclears`), обходы таблиц страниц по коду |
| d | uops из uop cache (DSB) и из декодера (MITE), обходы таблиц страниц по данным, попадания программного prefetch |
| e | branch misses (условные и все), попадания в STLB по данным и коду, восстановления после ошибок |

## Setup

Конфигурацию latency-critical системы я повторял по [Low latency tuning guide Эрика Ригторпа](https://rigtorp.se/low-latency-guide/). Оттуда же идея запретить глубокий сон на критичном ядре. Всё ставится скриптом [setup.sh](setup.sh). Перезагрузку настройки не переживают. Проверить, что они на месте, можно скриптом [check.sh](check.sh).

| Настройка | Зачем |
| --- | --- |
| SMT выключен | У ядра замера нет соседнего потока, который делит с ним L1, L2 и BTB |
| Turbo выключен, частота закреплена на базовой (3,2 ГГц) | Частота не плавает, и наносекунды можно сравнивать между запусками |
| `irqbalance` остановлен, все IRQ на ядрах 0–4 | Прерывания устройств не заходят на ядро замера |
| `workqueue/cpumask` — только ядра 0–4 | Фоновая работа ядра ОС не попадает на ядро замера |
| systemd: все слайсы на ядрах 0–4, `bench` в своём слайсе на ядре 5 | Ядро 5 отдано только замеру. Это вариант `isolcpus` без перезагрузки |
| C-состояния на ядре замера ([cstate.sh](cstate.sh)) | `0` оставляет только POLL, как на критичном ядре в проде. `3` разрешает состояния до C3 включительно. `9` разрешает все состояния, как по умолчанию, и за паузу 10 мс ядро уходит в C6 и глубже. `3` и `9` нужны для сравнения. Они показывают, что будет, если разрешить ядру глубокий сон, и дают заведомо холодный обработчик, на котором видно, что именно теряется. Остальные ядра остаются с настройками по умолчанию |
| Transparent huge pages выключены | `khugepaged` не перекладывает память под замером |
| NMI watchdog выключен | Нет периодического NMI на каждом ядре, и счётчик процессора свободен |
| `kernel.sched_rt_runtime_us = -1` | RT-троттлинг не прерывает `SCHED_FIFO`-поток в цикле |
| `kernel.perf_event_paranoid = -1` | Счётчики можно читать `rdpmc` из пользовательского пространства |
| `vm.stat_interval = 120` | Сбор статистики памяти заходит на ядро раз в 2 минуты, а не каждую секунду |
| Автообновления остановлены | Во время серий нет посторонней нагрузки |
| `bench`: `SCHED_FIFO`, `mlockall`, timer slack 1 нс | Нет вытеснения и page faults, и сон просыпается точно в срок |
| `nohz_full=2-5 rcu_nocbs=2-5` в загрузке (только серии с тиком) | Убирает тик таймера и RCU-колбэки с ядер замера |

Кое-что из гайда я не сделал. Ядро изолировано через systemd, а не параметром загрузки `isolcpus`, чтобы не перезагружать сервер. Защиты от Spectre (`mitigations`) оставлены по умолчанию.

Подробности по отдельным настройкам есть в документации ядра Linux. Это страницы [CPU isolation](https://docs.kernel.org/admin-guide/cpu-isolation.html), [NO_HZ](https://docs.kernel.org/timers/no_hz.html) и [cpuidle](https://docs.kernel.org/admin-guide/pm/cpuidle.html).

## Главное

Первые замеры сделаны на Intel i7-8700 с обработчиком [CppTrader](https://github.com/chronoxor/CppTrader). Горячий вызов на этой машине занимает 117 нс.

- Ядро, которое не спит, всё равно остывает. Первый вызов после 10 мс цикла на 130–150 нс дольше горячего. Теряется фронтенд (L1i, BTB). Половину вреда даёт тик таймера.
- Shadow execution каждые 50 мкс сокращает штраф почти до нуля за 0,2–0,3% ядра. Но его цена растёт с размером обработчика и у большого доходит до 47%.
- Prefetch возвращает кэши, но не фронтенд. Поэтому у маленького обработчика он слабее shadow execution. Зато у большого кода (128 КБ) он сокращает штраф на 96% за 3,3% ядра, а shadow execution сокращает его на 76% за 16%.
- На живом Bitstamp feed shadow execution снизил p999 самого обработчика с 1222 до 907 нс в потоке одной пары. В replay на Broadwell выигрыш полного p99 относительно `spin` не подтвердился.
- Сосед по общему L3 делает цикл в 17 раз дороже (1749 против 102 нс). Shadow execution возвращает его к 79 нс, а prefetch к 311 нс.

В роли обработчика CppTrader (MIT). Он разбирает ITCH 5.0, ведёт стакан по заявкам и вызывает стратегию. Код CppTrader я не меняю, моя обёртка лежит в [src/handler/cpptrader.cpp](src/handler/cpptrader.cpp). Для замера я беру событие Add Order по лучшему bid и Delete этой заявки, поэтому стакан после него тот же. Обработчик из открытого проекта я взял потому, что это честнее, чем собственный упрощённый.

## Сборка

Нужны Linux, CMake и GCC 13 или новее (C++23).

```bash
./get-cpptrader.sh && ./get-itch.sh   # third_party/ и день Nasdaq BX в data/
cmake -S . -B build && cmake --build build -j
```

| Каталог | Что внутри |
| --- | --- |
| `src/common/` | время, окно TSC, привязка к ядру, опции, ITCH и MoldUDP64 |
| `src/handler/` | обработчики `cpptrader`, `synth` (синтетика) и `null` (калибровка окна), дополнительная нагрузка для обработчиков разного размера и отправка заявки. Обработчик выбирается при сборке |
| `src/bench/` | замер холодного вызова. Горячие вызовы, пауза, потом 8 замеренных вызовов в CSV |
| `src/recv/` | приёмник онлайн-стенда. Multicast, обработчик, журнал `.rec` |
| `src/neighbour/` | фоновая нагрузка для серий изоляции |
| `src/feed/` | коннектор Bitstamp → ITCH → multicast, запись и воспроизведение |

## Запуск

```bash
./setup.sh                    # после каждой загрузки, проверка — ./check.sh
./cstate.sh 0                 # только POLL на ядре замера (9 — по умолчанию)
./run.sh quick --trials 100   # один прогон bench → results/<время>-<имя>/
python3 analyze.py results/<время>-quick/calls.csv
```

Режимы паузы `bench` (`--conds`):

| Режим | Между горячими вызовами и замером |
| --- | --- |
| `hot` | ничего |
| `spin` | busy-poll цикл длиной Δt |
| `spinshadow` | тот же цикл, каждые T — shadow execution |
| `spinpf` | тот же цикл, каждые T — prefetch |
| `none` | сон Δt |
| `shadow` | сон с пробуждениями каждые T и shadow execution |
| `prewake` | сон, пробуждение за δ до события (δ = 200 мкс), shadow execution, остаток ожидания в цикле |
| `pfwake`, `pfevent` | как `prewake` и `none`, но вместо прогона prefetch (до события или в его момент) |
| `empty`, `cold`, `sys`, `dis` | режимы для проверки и разбора. Пробуждения без прогрева, вытеснение кэшей, один системный вызов, точечная порча отдельных структур процессора |

Серии из документов запускаются скриптами [pf.sh](pf.sh) (prefetch и shadow execution), [size.sh](size.sh) (размер обработчика), [iso-night.sh](iso-night.sh) (изоляция) и [nzt.sh](nzt.sh) (тик таймера). Онлайн-стенд поднимают [setup-online.sh](setup-online.sh) и [online.sh](online.sh). Как ими пользоваться, написано в шапке скрипта. Хвосты разбирает [tails.py](tails.py). Графики к документам строит [docs_figures.py](docs_figures.py), русские подписи к ним лежат в [docs/figures.ru.json](docs/figures.ru.json). Полный набор графиков строит [figures.py](figures.py).
